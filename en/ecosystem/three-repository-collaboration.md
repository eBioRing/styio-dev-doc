# 三仓库协作指南

本页旨在为 `styio`、`Spio`、`Vityo` 的跨仓协作提供推荐的流程概览。通过明确各仓库的语义边界与协作共识，我们旨在提升整个生态的协作效率。

关于许可证、依赖合规等统一标准，请参考 [审计与合规](../standards/audit-license-and-dependency-policy.md)。

## 协作模型

在 Styio 生态中，我们通过以下协作身份来维持各仓库的解耦：

| 仓库 | 核心角色 | 协作共识 |
| --- | --- | --- |
| `styio` | 上游语义源 | 定义核心语法、语义与 `styio-protocol` 公共接口。 |
| `Spio` | 包生态消费方 | 负责包管理与工作流，通过公开契约与编译器交互。 |
| `Vityo` | 交互与视图消费方 | 提供 IDE 与可视化能力，消费编译器提供的分析事实。 |

## 协作原则

1. **契约驱动**：`styio` 定义稳定的公共接口与 `styio-protocol`，其他工具基于这些接口提供服务。
2. **职责清晰**：`Spio` 和 `Vityo` 专注于各自的业务领域，不反向修改语言的核心语义。
3. **流程沉淀**：通用的协作流程先在此处探讨，待稳定后再沉淀至各项目的本地文档。
4. **自主闭环**：每个仓库独立维护其代码、测试与交付门禁，确保各组件的健壮性。
5. **平滑演进**：涉及跨仓的变更应预留兼容窗口，提供验证方案以降低迁移成本。

## `styio-protocol`：生态的交接纽带

`styio-protocol` 是连接编译器与周边工具的静态协议。它定义了各组件之间如何“握手”，而不是源码级的耦合。

它涵盖以下协作面：

1. **命令行契约**：公开的 CLI 参数、退出码与文件交互约定。
2. **能力握手**：`styio --machine-info=json` 提供的版本与功能元数据。
3. **执行计划**：`styio --compile-plan <path>` 的 schema 与执行语义。
4. **语义载荷**：JSON/JSONL 格式的诊断、运行事件、Token 范围等公共数据。

通过这种方式，我们确保了包管理器或 IDE 可以在不链接编译器私有模块的情况下，稳定地调用其核心能力。

## 语法更新的协同建议

当 `styio` 引入新语法时，我们建议通过以下方式引导 `Vityo` 与 `Spio` 同步：

- **上游（`styio`）**：在完成语法实现后，提供可验证的样例与 Token 范围等机器可读的事实，并在协议文档中同步说明。
- **下游（`Vityo` / `Spio`）**：依据编译器提供的稳定事实，更新高亮、补全、诊断呈现或工作流逻辑。
- **需求反馈**：如果下游发现基础接口不足以支持产品交互（如 IDE 需要更细粒度的分析），建议向 `styio` 提出接口改进建议，而非在下游绕过接口自行实现。

## 推荐的工作流阶段

为了确保大型改动的平稳落地，建议参考以下协作阶段：

1. **共识起草**：在 `styio-dev-doc` 中明确变更目标、受影响接口及各仓的协作重心。
2. **接口先行**：优先在 `styio` 侧冻结接口形状，为下游开发提供稳定的基准。
3. **独立实现**：各仓库依据共识，在各自仓内完成功能闭环与自动化验证。
4. **文档同步**：将协作结论同步至各项目仓库的本地文档，并更新对应的维护手册。

## 变更类型参考矩阵

| 变更场景 | 驱动方 | 协同方 | 验证建议 |
| --- | --- | --- | --- |
| 语法/诊断更新 | `styio` | `Vityo` (交互) | 跑通编译器 Pipeline 与 IDE 交互测试 |
| 编译器新发版 | `styio` | `Spio` (托管) | 更新兼容矩阵并验证工具链生命周期 |
| IDE 深度分析需求 | `Vityo` | `styio` (接口) | 补全 IDE Service 接口并通过适配测试 |
| 包管理策略变更 | `Spio` | `styio` (协议) | 验证 Registry 交互与 Resolver 逻辑 |

这种矩阵旨在帮助维护者快速识别受影响的节点，确保协作不留死角。
