# Testing and Regression Strategy

Styio maintenance cannot rely on visual diff inspection. Every change should land in at least one class of automated check.

## Which Tests Must Cover a Change?

According to `AGENT-SPEC.md`, every functional change should consider at least:

| Change type | Minimum validation |
| --- | --- |
| New token | lexer sample, `--debug` when needed |
| New syntax | parser sample, `--styio-ast` |
| Type-system change | type inference validation, `--styio-ast` |
| IR / codegen change | `--styio-ir` / `--llvm-ir` / execution result |
| Runtime behavior change | JIT execution result and related C++ tests |

## Current Test Surface

The main repository currently has at least these layers:

- `tests/milestones/`
- `tests/pipeline_cases/`
- `tests/security/`
- `tests/soak/`
- `tests/fuzz/`
- `tests/lit_cases/`

And these CTest registrations:

- `docs_audit`
- milestone tests
- parser shadow gates
- `styio_test`
- `styio_security_test`
- `styio_soak_test`

Current `styio@nightly` also treats these as formal maintenance assets:

- `docs/assets/workflow/TEST-CATALOG.md`
- `scripts/docs-index.py`
- `scripts/docs-audit.py`

The test surface therefore includes not only source and golden files, but also documentation tree consistency.

## Common Commands for Maintenance

Full suite:

```bash
ctest --test-dir build --output-on-failure
```

Milestones:

```bash
ctest --test-dir build -L milestone --output-on-failure
```

Five-layer pipeline / shadow:

```bash
ctest --test-dir build -L styio_pipeline --output-on-failure
```

Security regression:

```bash
ctest --test-dir build -L security --output-on-failure
```

Soak smoke:

```bash
ctest --test-dir build -L soak_smoke --output-on-failure
```

Single case:

```bash
ctest --test-dir build -R '^m10_t01_stdin_echo$' --output-on-failure
```

Documentation audit:

```bash
ctest --test-dir build -L docs --output-on-failure
```

Rebuild documentation index:

```bash
python3 scripts/docs-index.py --write
python3 scripts/docs-audit.py
```

## Regression Rule

One core principle:

**Existing tests should not be broken without explanation.**

If an existing test must change, synchronize at least:

- the reason for the change
- the corresponding design / specification document
- related golden files
- test directory or test-directory explanation

## Correct Role of Milestones

Milestone documents do not exist to tell history. They freeze acceptance boundaries.

The useful maintenance facts are:

- which capability is frozen
- where the corresponding sample lives
- whether it is stdout comparison, stderr comparison, or side-effect file comparison
- which `ctest` label or gate it maps to

## Why the Five-Layer Pipeline Matters

Styio is no longer checked only by "does it run". The five-layer pipeline freezes:

- token
- AST
- Styio IR
- LLVM IR
- final output

This is especially important for people changing parser, IR lowering, and codegen.

## Treat Documentation Tests as Real Tests

`styio@nightly` has formalized documentation tree maintenance:

- `docs/README.md` defines directory boundaries
- `docs/INDEX.md` is generated by script
- `docs_audit` is part of `ctest`
- `TEST-CATALOG.md` is the test map

If you change:

- docs tree structure
- test directories
- milestone orchestration
- handoff / workflow assets

then the minimum loop is not just `ctest -L milestone`; it should also include docs index and docs audit.
